## 改用同步码方案（commit f5f1255）

用户决定放弃邮箱 OTP，改用同步码。核心改动：

- **身份**：8 位同步码（字符集去掉易混淆的 I/L/O/0/1，共 31 个），拒绝采样消除模偏差。
  绑定/解绑/换码，存 localStorage（`esp_sync_code_v1`），无注册无邮箱。
- **安全关键**：同步码无 JWT，RLS 的 auth.uid() 恒空，若沿用旧「策略+直接读写表」等于
  允许匿名 SELECT 全表。改为 **security definer RPC 作为唯一入口**：
  `supabase-sync-schema.sql` 撤销 anon 对 attempts 的直接权限，只暴露 `sync_pull(p_code)` /
  `sync_push(p_code, p_rows jsonb)`，内部按 normalize_code 过滤。拿不到码查不到数据。
- **去掉 SDK**：store.js 改用原生 fetch 调 `/rest/v1/rpc/*`，删掉 vendor/supabase.js（218KB），
  页面只剩 config/store/app 三个脚本。写策略：本地先落盘 + pending 队列 + 后台补传。
- **UI**：弹窗两个 tab（我的码 / 输入已有码），输入自动大写+补连字符，复制/换码/解绑。
- 冒烟测试 33/33 通过（/tmp/esp-sync-test.js）。
- **踩坑**：绑定后状态条没刷新——因为 bindCode 先 await sync() 再 emit，后端 404 往返慢
  导致 UI 延迟。改为先 emit 再后台 sync()，绑定立即生效。

**RPC 探测手法**：`POST /rest/v1/rpc/<name>` body 传参数，404 + PGRST202 表示函数不存在
（SQL 没执行）；`GET /rest/v1/attempts` 返回 200 空数组表示 anon 仍可读表（权限没收紧）。

**待用户操作**：在 Supabase SQL Editor 执行 `supabase-sync-schema.sql`（旧 supabase-schema.sql
已作废删除）。执行后验证三列自检 = 0/t/2。

- AI 对话：新增第 4 个 tab「AI 对话」，5 个角色（自由对话/服务员/面试官/店员/同事），
